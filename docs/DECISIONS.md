# Architecture decision log

[简体中文](DECISIONS.zh-CN.md) · [Documentation](README.md)

- **ADR-001 Accepted** — Use the current Daybreak repository organization as a reference: XcodeGen, `Apps/MacApp/{Core,UI,Localization,Tests}`, standalone Swift packages, `Platform/MacIntegration`, `docs`, and `branding`. BlueLink is macOS-only. Minimum deployment target: macOS 26.0. Swift 6 strict concurrency. Daybreak is read-only reference material; no code copied.
- **ADR-002 Accepted** — Public Apple APIs only. Device-level control. No private APIs, external CLIs, log parsing, UI automation, or private Bluetooth databases.
- **ADR-003 Accepted** — Pure policy table plus event-driven coordination. Value types for identity, events, and snapshots; protocols only at real platform boundaries; an actor for shared mutable state. Keep the actual connection, desired intent, operation in flight, and audio readiness separate. Observe and reconcile a stale callback; never silently drop it.
- **ADR-004 Accepted** — The user explicitly selects devices. Manual override, persistent pause, and bounded retry are supported. Audio switching is off by default. Pause does not change the current connection; an unknown state never triggers an automatic operation.
- **ADR-005 Accepted (implemented)** — `AppIcon.icon` is the only compiled app icon. It contains a gradient background and independent front/rear ribbon layers in the real Icon Composer document format. The legacy `AppIcon.appiconset` is renamed `AppIconLegacy.appiconset` to avoid a duplicate rendition; it remains a brand source and fallback and is not compiled. `ictool` rendered Default/Dark/ClearLight/ClearDark/TintedLight/TintedDark; `NSWorkspace` returns a 512 pt icon; Xcode compiles the `.icon` into `IconImageStack`.
- **ADR-006 Accepted (partially implemented)** — GitHub Actions builds and tests an ad-hoc artifact; `ci.yml` and `package-dmg.sh` exist. Even when CI is enabled, no release, asset upload, signing, or notarization occurs without user authorization. Name BlueLink, bundle identifier `dev.bluelink.mac`, and MIT license are set; final release identity still needs user confirmation.
- **ADR-007 Accepted** — Dark/tinted/clear appearances derive from the system; do not bake them separately. The rear ribbon uses `opacity: 0.72` so front and rear layers remain distinct in dark/tinted appearances. Default opacity remains 1.
- **ADR-008 Accepted** — Use `Localizable.xcstrings` and `InfoPlist.xcstrings`. Source language is English; zh-Hans is required. Do not use dynamic `Text(String)` for translatable literals. Conditional copy, `.help`, and error summaries use `LocalizedStringKey` or `LocalizedStringResource`. App tests check representative keys, interpolation formats, and Info.plist strings.
- **ADR-009 Accepted** — Diagnostics are local-only and redact Bluetooth addresses and device identifiers by default. Export is plain text. App-owned messages are localized with the UI; system errors keep the system language and technical wording, marked as system errors, rather than guessed translations.
- **ADR-010 Superseded by ADR-019** — The original manual-only update check remains as a fallback for builds without a Sparkle key. Without `BlueLinkUpdateRepository` or a valid `SUPublicEDKey`, Sparkle is disabled and no signed feed is used.
- **ADR-011 Accepted** — UI snapshot tests use `NSHostingView` and `cacheDisplay` to render real views offscreen. They exist only in the test target. The product has no debug window, test entry point, or fake data. Menu bar and Settings screenshots in the docs are labeled as offscreen renders.
- **ADR-012 Accepted** — The menu bar item follows macOS overflow rules. BlueLink does not create a persistent window or Dock icon to bypass hiding. When the menu bar is full, the item can be invisible; record this as a known limitation and do not use private APIs to force it visible.
- **ADR-013 Accepted** — Hardware tests require `BLUELINK_REAL_DEVICE=1`; device ID and name come from the environment. They are skipped by default. The test records the entry connection state and restores it on exit, so it does not leave the user's audio or connection state changed.
- **ADR-014 Accepted** — Bluetooth availability changes enter the coordinator through `.systemChanged`. At launch the controller may be unknown and then become available; this transition resets budgets and triggers one `bluetoothRecovered` reconcile. A wake cycle accepts only a confirmed display asleep→awake transition; display unknown→awake does not reset a manual-disconnect override or the drop budget. A late connect/disconnect completion must reconcile again; if the display slept or woke in the meantime, issue the corresponding disconnect/connect.
- **ADR-015 Accepted** — Besides the five-attempt backoff budget, automatic reconnect has a flapping limit: the fourth unexpected drop within 60 seconds stops automatic reconnect and marks `reconnectRateLimited`. The limit clears only on wake, Bluetooth recovery, an effective configuration change, or explicit retry. A successful connect does not clear it, preventing an unbounded connect/drop loop. After each connect/disconnect callback, the IOBluetooth disconnect registration is replaced; the old registration is released only after the new one succeeds. This lifecycle still needs two consecutive real drops to verify.
- **ADR-016 Accepted** — After `openSettings`, activate the app and call `makeKeyAndOrderFront`/`orderFrontRegardless`. The Settings view tags its hosting window with a stable identifier through an `NSViewRepresentable`, so the window rises when first shown and when the menu button is pressed again. Cross-application foreground activation still follows system policy; no private API is used.
- **ADR-017 Accepted** — The About page shows author Dylan Liu's public GitHub information (avatar, email, GitHub link). The avatar uses the same public GitHub URL as Daybreak and bundles the same image as an offline fallback, avoiding a letter placeholder on network failure. Copyright is © 2026 Dylan Liu; the MIT license and Info.plist copyright agree.
- **ADR-018 Accepted** — Settings and the Add Device sheet use a native `NSVisualEffectView` (`.underWindowBackground`, `.behindWindow`, `.active`) for a frosted window background. The hosting window is non-opaque with a clear background; the Form scroll background is hidden. Reduce Transparency falls back to an opaque `windowBackgroundColor`; Increase Contrast adds a semantic tint. Because `MenuBarExtra` gives a bare `ScrollView` no intrinsic height, the device list uses a 72–322 pt height based on device count and scrolls beyond five rows. A loading placeholder appears while the engine state is not ready, preventing a collapsed blank middle.
- **ADR-019 Accepted** — Use Sparkle 2.10.1 through Swift Package Manager for signed automatic updates. The stable feed is `https://github.com/mentalfl0w/BlueLink/releases/latest/download/appcast.xml`; `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction` are enabled, and the EdDSA public key is embedded in Info.plist. The private key exists only in the GitHub Actions `SPARKLE_EDDSA_PRIVATE_KEY_BASE64` secret and the maintainer's secure local store; it is never committed. CI generates and validates `appcast.xml` from the release ZIP and uploads it with stable releases only. Automatic checks and automatic downloads are off by default; the Settings toggles opt in. Sparkle may download in the background, then asks before installing when BlueLink quits. The app remains ad-hoc signed; Developer ID signing and notarization are separate distribution work.

## Open questions

- Real display sleep/wake, dark wake, and system sleep event order, latency, and failure modes. Policy tests exist; hardware does not.
- `SMAppService` login-item registration, approval, and restart behavior in a signed app bundle.
- Bluetooth TCC authorization persistence after the ad-hoc signature changes.
- End-to-end audio playback and preferred-output switching.
- Product-level mitigation when the menu bar is too crowded to show the item, without private APIs.
- Developer ID signing, notarization, and a non-ad-hoc update trust story remain open; Sparkle update installation must be verified on a released build before claiming distribution readiness.

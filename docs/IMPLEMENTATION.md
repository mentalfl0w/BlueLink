# Implementation plan

[简体中文](IMPLEMENTATION.zh-CN.md) · [Documentation](README.md) · [Verification](VERIFICATION.md)

BlueLink is an independent macOS project. It does not copy Daybreak code or features. The current Daybreak repository structure, contribution guide, and decision log are references only.

## Architecture

- **Core:** value types, minimal ports (`BluetoothClient`, `SystemStateSource`, `Clock`), a policy reducer, a state machine, and a coordinator with injectable time and transport. Foundation-only.
- **Platform:** system adapters, lifecycle notifications, device calls, audio, login item, configuration, and diagnostics. Depends on Core.
- **App:** `AppModel` is `@MainActor`; it subscribes to snapshots and exposes user intents. Views never hold a Bluetooth handle.
- Avoid empty DDD layers, duplicate stores, and one protocol per operation. Core and Platform are independently testable with `swift test`.
- `scripts/boundary-check.sh` enforces import boundaries and the public-API rules.

## Phase A — validation and skeleton

Check Swift, Xcode, macOS, and the local Daybreak organization (read-only). Confirm the bundle ID, minimum deployment target (26.0), Swift 6 strict concurrency, public IOBluetooth APIs, threading, notifications, and device enumeration. Verify display-state observation on the current Mac through the normal app path and tests, never a user-visible test mode. Mark missing hardware as Not tested. Generate a buildable app skeleton with XcodeGen.

## Phase B — P0 vertical slice

Implement `CONNECTION_POLICY` in Core with a fake clock and Bluetooth client. Cover rapid events, pause, timeout, and late callbacks. Connect Platform to workspace, display, and IOBluetooth. Implement device selection, state display, pause, manual actions, independent policy, and configuration restore in the app. Verify display sleep/wake and unexpected drops when an authorized device is available. Without hardware, still deliver a runnable slice and tests. Never hide defects behind a timer keepalive or global Bluetooth control.

## Phase C — productization

Complete Settings, permission and launch-at-login handling, optional preferred audio (off by default), localization, diagnostics, native appearance, real Icon Composer icon, and menu bar template. Exercise the full UI once; save real screenshots when available. Update checks stay disabled until a release repository is configured; use the GitHub Releases API with semantic version comparison and explicit network/error states. Do not invent remote URLs, versions, or release state. An ad-hoc build may offer a release download link but must not silently replace itself. Automatic installation requires signing and update-security prerequisites, with a separate ADR.

## Phase D — QA and delivery

Run the applicable tests in [Verification](VERIFICATION.md). Measure idle CPU, memory, absence of continuous Bluetooth operations, and event-to-connect latency separately from connection completion. Finish CI, unsigned builds, repeatable DMG/ZIP scripts, and an ad-hoc test copy when authorized. Developer ID signing and notarization are separate steps. Do not ship unfinished P0 items, fake data, or dead buttons. Mark unexercised scenarios Not tested. Update both language versions of the README, contributing guide, decisions, changelog, and verification evidence. Do not publish remotely without authorization.
